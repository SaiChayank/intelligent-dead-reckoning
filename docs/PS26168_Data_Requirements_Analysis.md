# PS26168 — Data Requirements Analysis

**Scope:** Identify the raw data, timing, labels, contextual state, and ground truth required by each major IDR subsystem. No dataset-selection decision, no feature definitions, and no model-architecture selection are made here.

**Constraint applied throughout:** deployable navigation must use only data available causally from the smartphone/edge sensors and explicitly permitted local map data. VBOX/CAN/reference channels may be used for training/evaluation labels only.

---

## 1. Phone-to-Vehicle Calibration

### Raw phone fields
- accelerometer xyz,
- gravity vector if available,
- gyroscope xyz,
- magnetometer xyz if used,
- sensor accuracy,
- exact sensor timestamps.

### GNSS context
- latitude/longitude,
- course/bearing when actually available,
- speed when actually available,
- provider accuracy,
- fix age/quality.

### Required temporal context
- stationary window for pitch/roll and bias estimation,
- straight-driving or sufficiently excited motion window for yaw/forward-axis alignment,
- remount/change detection history.

### Ground truth for development
- VBOX heading/velocity/acceleration where synchronized and semantically valid,
- known physical phone orientations from controlled device experiments.

### Critical caveat
IO-VNBD exported orientation/gravity/acceleration semantics are not universally established as raw Android device-frame channels. Calibration training/validation must not assume they are.

---

## 2. Classical INS Mechanization

### Required
- calibrated accelerometer/specific force,
- calibrated gyroscope,
- device→vehicle rotation,
- initial navigation origin,
- initial attitude,
- initial velocity,
- precise monotonic dt.

### Optional aiding
- magnetometer heading if validated,
- gravity sensor for calibration/diagnostics,
- GNSS only at explicitly allowed initialization/update times.

### Not permitted
- future GNSS,
- VBOX reference during deployable propagation,
- row index as time unless justified for that evaluation-only experiment,
- guessed axis mappings.

### Data-quality requirements
- duplicate detection,
- time gaps,
- out-of-order handling,
- sensor availability,
- nonfinite rejection,
- consistent units.

---

## 3. AI Speed / Vibration Filter

### Candidate deployable inputs
After source/frame validation:
- vehicle-frame accelerometer,
- vehicle-frame gyroscope,
- accelerometer magnitude,
- gyro magnitude,
- causal rolling statistics,
- optional gravity/magnetometer quality,
- calibration quality,
- historical predicted speed/state where architecture explicitly allows recurrence.

### Training labels
- VBOX/reference speed,
- optionally reference longitudinal acceleration,
- reference heading/course for analysis.

### Label alignment requirements
- synchronized sequence membership,
- exact/quantified timestamp relation,
- no future smoothing that leaks later reference data into current input,
- no row-pairing assumption beyond what evidence supports.

### Split requirements
- split by drive/recording group,
- never random-row split,
- keep duplicate copies in the same partition,
- freeze held-out sequences before tuning.

---

## 4. AI Fusion-Correction Model

This model is **not required before a classical EKF works**.

### Candidate inputs
- causal EKF state/residual features,
- innovation magnitude,
- GNSS quality,
- calibrated IMU summary,
- current covariance summary,
- speed/heading context.

### Labels
- reference position/velocity error relative to independent ground truth.

### Requirements
- target must not directly encode future trajectory information,
- training residuals should be generated by the same classical fusion implementation used at inference/replay,
- no VBOX field may enter inference features.

---

## 5. GNSS + INS Fusion

### GNSS observations
- lat/lon,
- altitude where valid,
- speed,
- bearing,
- horizontal/vertical accuracy,
- satellite use/quality,
- fix age,
- provider.

### INS state
- position,
- velocity,
- attitude,
- bias estimates,
- covariance.

### Timing
- measurement time, not callback wall time,
- monotonic clock domain,
- bounded late-event policy.

### Validation labels
- independent reference trajectory,
- masked-GNSS outage intervals.

### Required context
- accepted/rejected measurement reason,
- innovation/gating diagnostics,
- outage duration.

---

## 6. GNSS Quality / Outage Handler

Required raw/context fields:
- provider,
- permission state,
- last fix time,
- fix age,
- horizontal accuracy,
- satellite count/status where valid,
- availability/staleness,
- optional speed/bearing availability,
- engine innovation/gating result after fusion exists.

Outputs:
- unavailable / acquiring / good / degraded / stale / denied,
- reason codes.

No single threshold should be called validated before physical data supports it.

---

## 7. Non-Holonomic Constraints

Required:
- vehicle-frame velocity/state,
- speed estimate,
- yaw/heading,
- motion state,
- confidence that phone→vehicle calibration is valid.

Helpful context:
- low-speed/stop detection,
- turn rate,
- vehicle class if constraints differ.

Risk:
- applying "zero lateral velocity" blindly can be wrong under skids, motorcycles, parking maneuvers, or invalid mounting.

---

## 8. Map Matching

Required:
- WGS84 position,
- heading/course,
- speed,
- position uncertainty,
- timestamp,
- local road geometry/topology.

Road graph attributes ideally include:
- edge geometry,
- connectivity,
- directionality,
- road class,
- allowed traversal direction,
- optional speed limits/turn restrictions.

Output evaluation requires:
- matched edge/position,
- confidence,
- comparison to reference route when available.

Map tiles alone are insufficient.

---

## 9. Offline Routing / Re-routing

Required:
- routable road graph,
- origin,
- destination,
- current navigation position,
- vehicle constraints,
- route-cost policy.

Re-routing additionally needs:
- off-route detection,
- route-progress state,
- map-matched position,
- deterministic graph access.

This is product navigation data, not inertial-model training data.

---

## 10. Confidence / Uncertainty Calibration

Required:
- predicted covariance/uncertainty,
- true horizontal position error from independent ground truth,
- regime labels: GNSS good/degraded/denied/recovery,
- outage duration/distance,
- calibration state.

Need enough independent segments to assess empirical coverage.

Provider GNSS accuracy alone is not a fused-navigation confidence label.

---

## 11. Mobile Runtime Performance

Measure:
- IMU input rate,
- GNSS update rate,
- navigation output rate,
- per-stage latency,
- queue depth/high water,
- dropped/invalid/late counts,
- PSS/RSS,
- CPU usage where available,
- battery/thermal behavior for extended tests.

Target evidence:
- ~10 Hz navigation output on mobile,
- bounded memory/queues.

---

## 12. Edge / FOG Engine

Required:
- FOG IMU specification and raw stream,
- exact sample rate,
- units/axes,
- timestamp source,
- calibration data,
- GNSS/reference aiding interface if used,
- same canonical output semantics as mobile.

Performance evidence:
- sustained processing toward ~200 Hz,
- latency distribution,
- memory/CPU,
- model inference time,
- output accuracy.

The smartphone dataset cannot by itself prove FOG runtime behavior.

---

## 13. Recording / Replay / Interoperability

Required for every evaluation session:
- metadata,
- source,
- acquisition session ID,
- exact timestamps,
- units,
- nulls,
- device/sensor information,
- completion/recovery state,
- record counts.

Replay must preserve:
- event IDs,
- `t_ns`,
- `received_ns`,
- order,
- payload,
- original lineage through replay source mapping.

---

## 14. Map Data

Current offline map requires:
- vector tile data,
- local style,
- glyphs/fonts,
- attribution/license files,
- manifest/checksum,
- bounded geographic coverage.

Future map matching/routing additionally requires a road graph. It should not be inferred from rendered tiles at runtime.

---

## 15. Evaluation Ground Truth

Minimum ground truth for scientifically meaningful drift claims:
- accurate reference position,
- reference speed,
- reference heading when available,
- synchronized time base or quantified alignment,
- defined outage start/end,
- travelled reference distance.

Primary metrics:
- final outage position error,
- mean/RMSE position error,
- drift / reference distance,
- velocity MAE/RMSE,
- heading error,
- recovery convergence time,
- output rate/latency.

## 17. Data Prohibitions / Leakage Rules

Never use as deployable outage-model input:
- VBOX/CAN channels,
- future GNSS,
- future smoothed labels,
- test-sequence statistics fitted globally,
- post-outage recovery data to predict earlier outage state.

Never silently:
- convert unresolved units,
- rename world-like exported acceleration as device-frame acceleration,
- replace nulls with zero,
- repair corrupt recordings without explicit recovery evidence.
